## 4. 成本模型（本任务最有价值的发现，含一次被测量推翻的假设）

### 4.1 起初的假设是错的

`docs/performance.md` 早先版本写的是"代价 ≈ 可见卡片数 × 0.6 ms"。**这个数字是错的**：把单张卡的
`paint()` 直接计时（10% 缩放下 200 次取中位数）只有 **0.059 ms/张**，72 张可见 ≈ **4 ms**，与 46 ms 差一个数量级。
按这个错误模型我实现了"缩得太小的卡不画正文"（T-033 原方案），实测**毫无改善**（47.1 ms vs 47.0 ms），
于是按测量结果**回退**了该改动（代码不值得为 0 ms 改动观感）。

### 4.2 真正的成本：背景网格

用聚焦探针逐项排除（`%TEMP%\mcwr_probe\mcwr_pan_probe.py`、`mcwr_isolate_probe.py`）：

| 变量 | fit（10% 缩放，72 张可见卡） |
| --- | --- |
| 基线 | 45.9 ms |
| 隐藏**所有**卡片 | 42.8 ms ← 卡片不是成本 |
| `scene.setItemIndexMethod(NoIndex)` | 45.8 ms ← 索引不是成本 |
| `view.setOptimizationFlag(DontSavePainterState)` | 46.1 ms ← 绘制状态不是成本 |
| **`view.setCacheMode(CacheBackground)`** | **3.8 ms** ← 背景就是成本 |
| 换成**空场景**（同 sceneRect） | 0.7 ms ← 视图/场景机制本身不是成本 |

原因在 `BoardScene.drawBackground`：传入的 `rect` 是**场景坐标**，10% 缩放下 1400×900 窗口暴露约
**11240×8460 场景单位**，`GRID_STEP = 40` 于是要画 **492 条贯穿全屏的线**（每次都抗锯齿），约 40 ms；
而整块背景本身只有 2M 设备像素。**卡片总成本（4 ms）还不到它的十分之一。**

修复（T-033）：给网格加**设备像素间距下限** `MIN_GRID_DEVICE_STEP = 8.0`——间距小于 8 设备像素时不画网格
（`GRID_STEP=40` ⇒ **20% 缩放及以下**跳网格，25% 以上外观与原来逐像素相同），同时把线数上限钉在
`viewport_px / 8`。

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| fit（10%）整视口重绘 | 46.6 ms | **3.0 ms** |
| 100% 整视口重绘 | 8.8 ms | **8.2 ms**（不变） |
| 1000 卡 `pan16` / `panfull` | 45.7 / 45.8 ms | **3.7 / 3.4 ms** |

真实平台前后对比图（同一窗口、同一 fit 缩放）：`spikes/_out/grid_floor_before.png` / `grid_floor_after.png`；
用像素统计确认（背景区域 `before` 3 种颜色含两条网格色，`after` **只有 1 种** `#191d22`）——**看预览图会
因缩放出现摩尔纹假象，必须用像素数据复核**。

### 4.3 一条工具陷阱（浪费了三次探针）

PySide6 里**给已存在的实例/类 monkeypatch 一个 C++ 虚函数（`BoardScene.drawBackground`、
`QGraphicsView.paintEvent`）是无效的**：Shiboken 在类创建时就解析了虚函数表，之后改 Python 类属性不会
影响派发。我据此得到过"关掉网格没变化"的**假阴性**结论。正确做法：①要改虚函数就改**源码**或**子类**；
②任何"补丁无效/无变化"的结论都要先用计数或日志证明**补丁真的执行过**（本轮 `grid lines 0` 就是那个证据，
我当时忽略了它）；③优先用不依赖虚函数派发的真实开关（`CacheBackground`、空场景、隐藏 item）。
